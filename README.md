# ترب تعمیر — نمونهٔ نمایشی مقایسهٔ خدمات تعمیر خودرو

نمونهٔ اجرایی یک محصول برای **فهمیدن هزینهٔ تعمیر خودرو پیش از مراجعه**: درخواست مشتری با
کمک هوش مصنوعی روشن می‌شود، پیشنهاد متخصصان قابل مقایسه می‌شود، توافق و هر تغییر هزینه
نسخه‌دار ثبت می‌شود، رسیدها به تأیید صریح مشتری می‌رسند و اگر اختلافی با توافق حل نشود،
حکم لازم‌الاجرای هوش مصنوعی دربارهٔ اقلام و مبلغ همان پرونده ثبت و ابلاغ می‌شود.

> **این یک نصب نمایشی است.** همهٔ حساب‌ها، قیمت‌ها، پرداخت‌ها، پاسخ‌های هوش مصنوعی و
> سوابق «مرجع بازار» نمونه‌اند. هیچ وجهی واقعاً منتقل نمی‌شود، هیچ اتصال زنده‌ای به ترب
> وجود ندارد و این پروژه وابستگی رسمی به ترب ندارد.

## راهنمای سریع: اجرا و آزمون

سه مسیر مستقل. هر سه از ریشهٔ مخزن شروع می‌شوند و جزئیات هرکدام در بخش‌های بعدی است.
پیش از شروع، `uv`، Node و Docker باید در دسترس باشند — [پیش‌نیازها](#پیشنیازها).

### الف) اجرای دمو بدون کلید مدل

بار اول، به همین ترتیب:

```bash
cp .env.example .env
docker compose up -d db
cd backend && uv sync --locked --extra dev
uv run alembic upgrade head
uv run python -m app.seed
cd ../frontend && npm ci && npm run api:types
```

سپس هر بار، از ریشهٔ مخزن، فقط:

```bash
uv run --project backend python scripts/dev.py --with-db
```

این دستور API، worker و رابط را با هم بالا می‌آورد. رابط روی
<http://127.0.0.1:3000> است. در صفحهٔ ورود، `customer-sahar` را انتخاب کنید و یک درخواست
تعمیر بسازید؛ برای دیدن سمت متخصص، در مرورگر دیگری با `specialist-arya` وارد شوید.
`AI_MODE=mock` پیش‌فرض است، پس پاسخ‌های دستیار نمایشی‌اند و هیچ کلید یا تماس پولی لازم نیست.
برای توقف، `Ctrl+C`؛ پایگاه داده با `docker compose down` خاموش می‌شود.

### ب) اجرا با AI واقعی (AvalAI)

در `.env` ریشه این چهار مقدار را بگذارید و بقیه را دست نزنید:

```dotenv
AI_MODE=live
AI_API_KEY=...
AI_ENFORCE_COST_CAP=false
WORKER_LEASE_SECONDS=600
```

`AI_PROVIDER=avalai`، `AI_MODEL=glm-5.3-flash` و آدرس درگاه از پیش‌فرض برنامه می‌آیند.
پیش از اجرای محصول، اتصال را جدا بسنجید — این دستور یک درخواست واقعی می‌فرستد:

```bash
cd backend && uv run python -m app.check_avalai --live
```

اگر `smokePassed: true` دید، `scripts/dev.py` را دوباره اجرا کنید تا API و worker با
تنظیمات تازه بالا بیایند. `AI_ENFORCE_COST_CAP=false` فقط کنترل هزینهٔ روزانه را برمی‌دارد؛
سهمیهٔ نوبت و توکن هر پرونده سر جایش است. جزئیات در [اتصال درگاه AvalAI](#اتصال-درگاه-avalai).

### ج) آزمون

هیچ‌کدام کلید مدل یا تماس پولی لازم ندارند:

```bash
docker compose --profile test up -d db-test
cd backend
uv run alembic -x test=true upgrade head   # فقط بار اول
uv run pytest                              # ۲۰۴ تست
uv run ruff check . && uv run mypy app
cd ../frontend && npm run test:e2e         # Playwright، پایگاه و پورت مجزای خودش
```

`uv run pytest` حدود دو دقیقه طول می‌کشد و به پایگاه تست روی پورت ۵۴۳۸ نیاز دارد. برای یک
فایل مشخص: `uv run pytest tests/test_avalai_provider.py`. تنظیمات AI در تست‌ها همیشه روی
mock قفل می‌شود، حتی اگر `.env` شما live باشد. فهرست کامل در
[آزمون و کنترل کیفیت](#آزمون-و-کنترل-کیفیت).

## پیش‌نیازها

| ابزار | نسخه | توضیح |
| --- | --- | --- |
| Python | ۳٫۱۳ | با [uv](https://docs.astral.sh/uv/) مدیریت می‌شود؛ `uv` خودش نسخهٔ لازم را می‌آورد |
| Node.js | ۲۴ | همراه npm |
| PostgreSQL | ۱۸ | یا با Docker Compose، یا نصب موجود با تنظیم `DATABASE_URL` |

نصب uv: `curl -LsSf https://astral.sh/uv/install.sh | sh`

`uv` باید در PATH باشد؛ اگر `Command 'uv' not found` دیدید، پوشهٔ نصب (معمولاً
`~/.local/bin`) در PATH نیست. `scripts/dev.py` هم درون خودش `uv run` صدا می‌زند، پس بدون
آن اجرا نمی‌شود. `npm ci` روی Node 22 هشدار `EBADENGINE` می‌دهد؛ ساخت و اجرای رابط با آن
آزموده شده و کار می‌کند، ولی نسخهٔ مبنای پروژه ۲۴ است.

## اولین راه‌اندازی، گام به گام

ترتیب زیر مهم است: هیچ اسکریپتی به‌جای شما وابستگی نصب نمی‌کند، migration اجرا نمی‌کند یا
داده پاک نمی‌کند.

```bash
# ۰) تنظیمات
cp .env.example .env          # نیازی به کلید مدل نیست

# ۱) پایگاه دادهٔ محلی (یا DATABASE_URL را به نصب موجود بدهید)
docker compose up -d db

# ۲) وابستگی‌های بک‌اند
cd backend && uv sync --locked --extra dev

# ۳) ساخت schema — همیشه صریح و پیش از اجرای API و worker
uv run alembic upgrade head

# ۴) دادهٔ نمونه (تکرارپذیر؛ دادهٔ موجود را پاک نمی‌کند)
uv run python -m app.seed

# ۵) وابستگی‌های رابط و تولید typeها از قرارداد
cd ../frontend && npm ci && npm run api:types
```

### اجرا

ساده‌ترین راه، اجرای هماهنگ هر سه سرویس است:

```bash
uv run --project backend python scripts/dev.py --with-db
```

بدون `--with-db` از پایگاه ازپیش‌آماده استفاده می‌شود. برای اجرای دستی:

```bash
cd backend && uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
cd backend && uv run python -m app.worker
cd frontend && npm run dev -- --hostname 127.0.0.1 --port 3000
```

- رابط: <http://127.0.0.1:3000>
- مستندات API: <http://127.0.0.1:8000/api/docs>

مرورگر فقط با origin رابط حرف می‌زند؛ Next.js درخواست‌های `/api` را بدون اجرای هیچ قاعدهٔ
محصولی به FastAPI عبور می‌دهد، بنابراین CORS باز یا دسترسی مستقیم به پورت API لازم نیست.

**worker را حتماً اجرا کنید.** مهلت‌ها، داوری، ارزیابی و انتقال بازپرداخت کار اوست؛ بدون
آن، مهلت ۲۴ ساعته هرگز اعمال نمی‌شود.

## ورود با حساب‌های نمونه

ثبت‌نام عمومی، پیامک و شمارهٔ تلفن واقعی وجود ندارد. در صفحهٔ «ورود با حساب نمونه» یکی از
این حساب‌ها را انتخاب کنید:

| نقش | حساب‌ها |
| --- | --- |
| مشتری | `customer-sahar`، `customer-omid` |
| متخصص مرتبط | `specialist-arya`، `specialist-behnam`، `specialist-kaveh` |
| متخصص نامرتبط (عمداً) | `specialist-rasht` (شهر دیگر)، `specialist-heavy` (خودروی دیگر)، `specialist-body` (تخصص دیگر) |
| پشتیبانی | `support-mina` |

نشست و کنترل دسترسی واقعی و سمت سرور است: توکن نشست هش‌شده ذخیره می‌شود، کوکی HttpOnly و
SameSite=Lax است، و هیچ فیلدی در بدنهٔ درخواست نمی‌تواند نقش تازه‌ای بدهد. متخصصان آرشیوی
(`archive-*`) فقط پشتوانهٔ دادهٔ مرجع‌اند و در فهرست ورود نمی‌آیند.

## هوش مصنوعی: نمایشی در برابر واقعی

| | `AI_MODE=mock` (پیش‌فرض) | `AI_MODE=live` |
| --- | --- | --- |
| کلید مدل | لازم نیست | `AI_API_KEY` الزامی است |
| شبکه | هیچ | DeepSeek از طریق LangChain یا درگاه AvalAI |
| پاسخ‌ها | از قواعد و سناریوی نمونه، با برچسب «پاسخ نمایشی» | از مدل پیکربندی‌شده |
| هزینه | صفر | مطابق تعرفهٔ ثبت‌شده |

**اجرای پیش‌فرض کاملاً بدون کلید کار می‌کند.** پاسخ‌های نمایشی همه‌جا برچسب دارند و هرگز
به‌عنوان اجرای مدل واقعی معرفی نمی‌شوند؛ قالب‌های آن‌ها هم عمداً مستقل از خروجی live
نوشته شده‌اند تا قبولی دمو با آزمون مدل اشتباه گرفته نشود.

برای حالت live این متغیرها لازم‌اند و نبودشان خطای روشن می‌دهد (نه بازگشت بی‌صدا به پاسخ
ساختگی):

```bash
AI_MODE=live
AI_API_KEY=...
AI_INPUT_PRICE_PER_MILLION=...     # تعرفهٔ ثبت‌شده به تومان
AI_OUTPUT_PRICE_PER_MILLION=...
AI_TARIFF_RECORDED_AT=2026-09-20
AI_DAILY_COST_CAP_TOMAN=...        # سقف روزانهٔ کل نصب؛ صفر یعنی هیچ فراخوانی live
```

### اتصال درگاه AvalAI

تنظیمات زیر را در `.env` ریشه قرار دهید؛ کلید، کلید شخصی حساب AvalAI است و فقط در
بک‌اند می‌ماند. `AI_PROVIDER`، `AI_MODEL` و `AI_BASE_URL` همین مقادیر را به‌صورت پیش‌فرض
دارند و نوشتنشان فقط برای صراحت است؛ `AI_MODE` و `AI_API_KEY` واقعاً لازم‌اند:

```dotenv
AI_MODE=live
AI_PROVIDER=avalai
AI_MODEL=glm-5.3-flash
AI_BASE_URL=https://api.avalai.ir/v1
AI_API_KEY=...
AI_REQUEST_TIMEOUT_SECONDS=180
WORKER_LEASE_SECONDS=600
AI_ENFORCE_COST_CAP=false
```

برای سنجش محلی، `AI_ENFORCE_COST_CAP=false` کنترل هزینهٔ روزانه را غیرفعال می‌کند؛
مصرف واقعی هر فراخوانی ثبت می‌شود و بدون تعرفه، هزینهٔ تومانی نامعلوم می‌ماند.
سهمیهٔ نوبت و توکن پرونده مطابق قواعد محصول برقرار است. برای برگرداندن کنترل روزانه،
این گزینه را `true` کنید و سقف و تعرفه را تنظیم کنید. پس از تغییر `.env`،
API و worker را دوباره اجرا کنید. کلید در بک‌اند می‌ماند و متغیر عمومی Next.js ندارد.
برای آزمون مستقل اتصال و قالب خروجی، از پوشهٔ `backend` اجرا کنید:

```bash
uv run python -m app.check_avalai --live
AI_MODE=mock uv run pytest tests/test_avalai_provider.py tests/test_check_avalai.py
```

در محیط محلی آماده‌شده، بدون نیاز به `uv` در PATH نیز می‌توانید
`.venv/bin/python -m app.check_avalai --live` را از `backend` اجرا کنید.

این دستور ورودی انگلیسی می‌فرستد و خروجی فارسی می‌خواهد. برای تست مستقل با متن کاربر
و دستورِ فارسی، داخل `backend` اجرا کنید:

```bash
.venv/bin/python -m app.check_avalai_fa --live
```

تست فارسی مدل‌های `COMPARISON_MODELS` را با ورودی و سقف خروجی یکسان بررسی می‌کند؛
در این نصب `deepseek-v4.1-flash` و `glm-5.3-flash`، یعنی همان دو مدلی که کلید حساب به
آن‌ها دسترسی دارد. خطای یک مدل مانع آزمون مدل‌های بعدی نیست؛ تنظیم مدل برنامه تغییر
نمی‌کند. برای هر مدل ورودی نمونه، پاسخ اعتبارسنجی‌شده، مصرف، زمان و خطا نمایش داده
می‌شود. موفقیت هر مدل با `smokePassed: true` مشخص می‌شود: پاسخ باید با schema منطبق باشد،
یک یا دو سؤال داشته باشد و در متن هر سؤال حروف خط فارسی/عربی دیده شود. تشخیص خط، ارزیابی
کیفیت زبان نیست؛ متن پاسخ برای بازبینی نمایش داده می‌شود. هر اجرا برای هر مدل موجود یک
درخواست تکمیل می‌فرستد. خلاصهٔ نهایی مدل‌های موفق، ناموفق و ناموجود را جدا نشان می‌دهد؛
فقط موفقیت همهٔ مدل‌ها کد خروج صفر دارد. بدون `--live` درخواست مدل ارسال نمی‌شود؛ پایگاه
داده یا API برنامه برای اجرای آن لازم نیست.

شناسه‌ای که در `/v1/models` درگاه نباشد با `model_not_advertised` گزارش می‌شود و برایش
درخواستی نمی‌رود، چون درگاه ممکن است نام ناشناخته را به مدل پیش‌فرض هدایت کند. برای آزمون
فقط یک مدل:

```bash
.venv/bin/python -m app.check_avalai_fa --live --model glm-5.3-flash
```

دستور `check_avalai` پس از کنترل فهرست مدل‌ها فقط **یک درخواست واقعی** با دادهٔ مصنوعی
می‌فرستد؛ مصرف، وضعیت پایان و انطباق با schema را گزارش می‌کند و retry ندارد. این ابزار
تشخیصی به پایگاه یا سهمیهٔ پرونده متصل نیست و مستقل از سقف روزانهٔ داخل محصول اجرا می‌شود؛
هزینهٔ تومانی بدون تعرفه گزارش نمی‌شود. `app.evaluate_model --live` نیز ارائه‌دهندهٔ
انتخاب‌شده را روی مجموعهٔ ۲۴ پرونده‌ای می‌سنجد و تست اتصال جای آن را نمی‌گیرد.

آداپتر AvalAI از Chat Completions متنی بدون ابزار و بدون ادامهٔ نشست استفاده می‌کند.
سقف خروجیِ رزروشده به‌صورت `max_tokens` در همان درخواست فرستاده می‌شود. HTTP 200
به‌تنهایی موفقیت نیست: `finish_reason`، بلوک `avalai` و JSON بررسی می‌شوند و اعتبارسنجی
نهایی Pydantic در سرویس برنامه باقی می‌ماند. مصرف پاسخ نامعتبر هم حفظ می‌شود؛ مقدار
جایگزین صفر/صفر در خطای درگاه، مصرف نامعلوم محسوب می‌شود. اگر درگاه `max_tokens` را
نادیده بگیرد، خروجی بیش از رزرو با `output_limit_exceeded` رد می‌شود؛ این کار مصرف
رخ‌داده را پس نمی‌گیرد. نبود retry داخلی و سقف سخت هزینه در سمت خود درگاه با تست آداپتر
اثبات نمی‌شود؛ هم‌ارزی این مسیر با API مستقیم DeepSeek ادعا نمی‌شود.

#### نتیجهٔ آزمون زندهٔ ۲۰۲۶-۰۹-۲۱

مقایسهٔ فارسی با ورودی یکسان و سقف خروجی ۶۵۰ توکن، پیش از فرستادن `max_tokens`:

| مدل | نتیجه | ورودی/خروجی | زمان |
| --- | --- | --- | --- |
| `glm-5.3-flash` | `smokePassed: true` | ۴۷۴ / ۵۲۳ | ۸.۹ ثانیه |
| `deepseek-v4.1-flash` | `output_limit_exceeded` | ۴۹۱ / ۹۰۵ | ۱۳.۱ ثانیه |

`glm-5.3-flash` پاسخ منطبق با schema و دو سؤال فارسی داد. `deepseek-v4.1-flash` با
`finish_reason: stop` پاسخ داد ولی خروجی‌اش از رزرو ۶۵۰ توکنی عبور کرد و رد شد؛ این مدل
`supports_reasoning` دارد و توکن استدلال در خروجی قابل‌صورتحساب حساب می‌شود. به همین دلیل
`glm-5.3-flash` مدل پیش‌فرض این نصب است. برخلاف مسیر قبلی، ورودی فارسی `content-blocked`
نگرفت.

این نتیجه یک آزمون اتصال دومدلی است، نه سنجش کیفیت: مجموعهٔ ۲۴ پروندهٔ live در این اجرا
سنجیده نشد و مسیر کامل محصول با AI واقعی جداگانه باید ضبط شود. تعرفهٔ تومانی تنظیم نشده
بود، پس `costToman` نامعلوم گزارش شد.

### مسیر یک پرونده

هشت اقدام، چهار از هر طرف. هر کدام یک تصمیم واقعی است، نه یک گام دفتری:

| # | مشتری | متخصص |
| --- | --- | --- |
| ۱ | ثبت درخواست — هزینهٔ ثبت در همان فراخوانی تسویه می‌شود | ثبت پیشنهاد |
| ۲ | پاسخ به پرسش‌های AI، سپس «تأیید و انتشار» | پذیرش انتخاب |
| ۳ | انتخاب پیشنهاد | شروع کار |
| ۴ | تأیید فاکتور نهایی — همین پرونده را می‌بندد | فاکتور نهایی با `final` |

پذیرش یک پیشنهاد **قطعی**، شروط همان پیشنهاد را مستقیم به جریان می‌اندازد: متخصص آن‌ها را
نوشته و مشتری همان‌ها را انتخاب کرده، پس توافق تازه‌ای برای تأیید نمی‌ماند. پیشنهاد
**مشروط** یا **عیب‌یابی** هنوز یک نسخهٔ مشخص بعد از بازدید می‌خواهد، چون مبلغش واقعاً به
نتیجهٔ بررسی بستگی دارد؛ نویسندهٔ آن نسخه تأییدش را همراه خودش ثبت می‌کند و فقط طرف مقابل
باید تأیید کند.

آنچه کوتاه نشده، چون قاعدهٔ محصول است: پذیرش دوطرفه پیش از شروع همکاری، دو تأیید صریح برای
هر **تغییر** توافق فعال، تأیید صریح مشتری روی همان نسخهٔ رسید، و کنترل زمان مراجعه هنگام
پیشنهاد، انتخاب، پذیرش و شروع.

### سه مرحلهٔ گفتگو

| مرحله | کجا | چه کسی |
| --- | --- | --- |
| ۱. شرح و تکمیل | `/requests/new` | مشتری؛ پرسش‌های لازم یکجا و سپس خلاصه |
| ۲. همکاری | `/requests/<id>/agreement` | مشتری و متخصص منتخب، با **سهمیهٔ مشترک** |
| ۳. محل و پایان | `/requests/<id>/completion` | تبدیل متن مخارج به اقلام و بازبینی متخصص |

کارهای کمکی — توضیح مقایسه، ارزیابی نهایی، بررسی انصاف قیمت و داوری اختلاف — بودجهٔ
جداگانه دارند. در مرحلهٔ دوم، حضور نفر دوم سهمیه را دو برابر نمی‌کند و تعویض متخصص هم آن
را بازنشانی نمی‌کند.

### سقف‌ها و مصرف

هر مرحله حداکثر ۳ نوبت موفق دارد و سهمیهٔ توکن جداگانه‌ای دارد. رزرو بودجه **پیش از**
فراخوانی و در تراکنش انجام می‌شود، بنابراین چند درخواست هم‌زمان نمی‌توانند با هم از سقف رد
شوند؛ هیچ قفل پایگاهی هم در زمان انتظار پاسخ مدل باز نمی‌ماند. فراخوانی پرداخت‌شده‌ای که
پاسخ نامعتبر داد، مصرفش ثبت می‌شود ولی نوبت موفق شخص را کم نمی‌کند. مصرف نامعلوم صفر
فرض نمی‌شود.

بررسی بازپرداخت، بازبینی امتیاز و داوری اختلاف هرکدام بودجهٔ عملیاتی مستقل دارند و به
مشتری صورتحساب نمی‌شوند. با پایان سهمیه، توافق، مشاهدهٔ پیشنهاد و درخواست بازپرداخت
همچنان فعال می‌مانند.

سیاست‌ها (آستانهٔ انصاف، آستانهٔ اختلاف فاحش فاکتور، حداقل سابقه، مهلت‌ها و سقف‌ها) همه در
یک محل تعریف شده‌اند: `backend/app/policy.py`. هر تصمیم، نسخهٔ سیاستی را که با آن گرفته
شده ذخیره می‌کند، پس کالیبراسیون بعدی نتیجهٔ قبلی را بازنویسی نمی‌کند.

## کنترل دمو و سناریوهای زمانی

با حساب پشتیبانی به `/support` بروید. آنجا صف بازپرداخت، اختلاف‌های متوقف‌شده، منابع قیمت
در انتظار تأیید، اعتراض‌های باز و سنجه‌ها را می‌بینید و می‌توانید:

- **شاهد تکمیلی به یک اختلاف اضافه کنید** و **بودجهٔ داوری را یک بار تمدید کنید**. نقش
  پشتیبان تکمیل شواهد و رفع انسداد است؛ حکم را صادر یا بازنویسی نمی‌کند و تسویهٔ اعمال‌شده
  را تغییر نمی‌دهد.

همچنین:

- **ساعت دمو را جلو ببرید** (فقط به جلو). مهلت ۲۴ ساعتهٔ پیشنهاد، ۲ ساعت پذیرش انتخاب،
  ۲۴ ساعت اظهارات اختلاف و ۴۸ ساعت تکمیل شواهد بدون انتظار واقعی آزمون می‌شوند. اختلاف
  ساعت در پایگاه ذخیره می‌شود، پس راه‌اندازی دوبارهٔ سرور آن را به عقب برنمی‌گرداند، و هر
  دو فرایند API و worker آن را می‌خوانند. بازگرداندن ساعت به زمان واقعی، کارهای در صف را
  هم به همان اندازه جابه‌جا می‌کند تا چیزی در آینده جا نماند. ساعت سیستم یا فایل‌های بیرون پروژه تغییر
  نمی‌کنند. طول عمر نشست عمداً با ساعت واقعی سنجیده می‌شود تا جلوبردن ساعت شما را از حساب
  بیرون نیندازد.
- **سیاست مبتنی بر مرجع را فعال کنید.** این پرچم فقط سناریوی سیاست داده‌محور را در دمو
  روشن می‌کند؛ نمونه‌های نمایشی هرگز یک گروه مقایسهٔ واقعی را «آماده» نمی‌کنند.
- **شکست بعدی درگاه پرداخت را صف کنید** تا مسیر تلاش مجدد انتقال را ببینید.

## نکته‌های مهم دربارهٔ آنچه ساخته شده

- **قیمت آزاد است.** هیچ کف، سقف یا تأیید هوش مصنوعی شرط ثبت یا انتخاب پیشنهاد نیست. فقط
  نقص ساختاری (فیلد لازم، دامنهٔ نامربوط، نوبت خارج از بازه) مانع ارسال می‌شود.
- **توافق با دو تأیید صریح روی همان نسخه فعال می‌شود.** سکوت تأیید نیست، تأیید نسخهٔ قدیمی
  به نسخهٔ تازه منتقل نمی‌شود، و نسخهٔ فعال قبلی تا دو تأیید نسخهٔ جدید سر جایش می‌ماند.
- **تأیید رسید مجوز افزایش مبلغ نیست.** هزینهٔ اضافی ابتدا باید از مسیر تغییر توافق بگذرد.
  رد رسید مسیر اصلاح یا اختلاف را باز می‌کند و حکم داوری نظر ثبت‌شدهٔ مشتری را عوض نمی‌کند.
- **حکم داوری بدون تأیید مجدد طرفین اعمال می‌شود**، ولی سرویس دامنه آن را پیش از اعمال
  اعتبارسنجی می‌کند: فقط دربارهٔ اقلام مورد اختلاف، بدون قلم تازه یا تکراری، بدون مقدار یا
  مبلغ بیشتر از ادعا، و فقط با شواهدی که واقعاً در ورودی همان بررسی بوده‌اند. مبلغ نهایی
  را کد محاسبه می‌کند. **اجرای حکم یعنی ثبت و ابلاغ نتیجه و مبلغ؛ وصول وجه تعمیر ساخته
  نشده است.**
- **قطعهٔ خریده‌شده توسط مشتری** در «مبلغ کل خدمت» هست ولی دوباره به «قابل پرداخت به
  متخصص» اضافه نمی‌شود.
- **قیمت ترب دستی ثبت می‌شود.** فقط لینک HTTPS با میزبان دقیق `torob.com` پذیرفته می‌شود و
  سرور آن را واکشی نمی‌کند. هشدار «اختلاف فاحش» فقط با حداقل سه قیمت هم‌مبنای تأییدشدهٔ
  پشتیبان و مشاهده‌شده تا ۲۴ ساعت پیش از خرید ساخته می‌شود؛ در غیر این صورت «قابل بررسی
  نیست» نمایش داده می‌شود و هیچ امتیاز منفی ثبت نمی‌شود. قیمت ارزان‌تر از ترب و قطعه‌ای که
  خود مشتری خریده هرگز امتیاز منفی نمی‌سازند.
- **امتیاز شفافیت هزینه** هرگز به‌صورت عدد تنها نمایش داده نمی‌شود: مخرج، دوره و تفکیک
  علت‌ها کنارش می‌آیند و زیر ۵ پروندهٔ قابل ارزیابی اصلاً عددی نشان داده نمی‌شود. کیفیت فنی
  تعمیر از این عدد نتیجه نمی‌شود و هیچ جریمهٔ مالی یا تعلیقی بر پایهٔ آن ساخته نشده است.
- **بازپرداخت**: استحقاق و انتقال دو رخداد مستقل‌اند؛ هر پرداخت حداکثر یک بازپرداخت کامل
  دارد؛ نتیجهٔ ردشده هیچ کار انتقالی نمی‌سازد؛ و تلاش مجدد از همان شناسهٔ انتقال استفاده
  می‌کند.

## آزمون و کنترل کیفیت

```bash
# پایگاه مجزای تست
docker compose --profile test up -d db-test

# بک‌اند
cd backend
uv run alembic -x test=true upgrade head   # فقط بار اول
uv run pytest
uv run ruff check .
uv run mypy app

# رابط
cd ../frontend
npm run typecheck
npm run lint
npm run api:check      # انطباق قرارداد، کد بک‌اند و typeهای تولیدشده
npm run test:e2e       # Playwright، روی پایگاه و پورت‌های مجزای خودش
npm run build
```

هیچ‌کدام از این‌ها به کلید مدل، تماس پولی یا اتصال زندهٔ ترب نیاز ندارند. هر تست pytest
روی schema اختصاصی خودش در پایگاه تست اجرا می‌شود و فقط همان schema را پاک می‌کند، پس
دادهٔ دمو دست‌نخورده می‌ماند. مهلت‌ها با ساعت تزریقی سنجیده می‌شوند، نه با انتظار واقعی.

مسیر `DeepSeekProvider` هم با شبکهٔ شبیه‌سازی‌شده آزموده می‌شود (نه فقط با جایگزینی
`MockAiProvider`): یک درخواست در هر تلاش، پارامتر صریح thinking، نبود retry داخلی در
timeout و 429، ثبت مصرف حتی برای JSON نامعتبر، و نشمردن دوبارهٔ توکن استدلال.

### تغییر قرارداد API

قرارداد از کد تولید می‌شود و typeهای رابط از قرارداد. فایل `frontend/src/lib/api-types.ts`
هرگز دستی ویرایش نمی‌شود:

```bash
cd backend && uv run python -m app.export_openapi
cd ../frontend && npm run api:types && npm run api:check
```

## ساختار پروژه

```
backend/app/
  api/         # مسیرها، وابستگی‌ها، تبدیل خطا، واحد کار هر درخواست
  domain/      # همهٔ قواعد محصول: مالی، نسخه، زمان، مجوز، داوری
  models/      # جدول‌ها و قیدهای پایگاه
  providers/   # آداپتر AI (mock و DeepSeek) و شبیه‌ساز پرداخت
  schemas/     # قراردادهای Pydantic برای API و خروجی مدل
  worker.py    # صف پایدار: مهلت‌ها، داوری، ارزیابی، انتقال
  policy.py    # تنها محل تعریف آستانه‌ها، سهمیه‌ها و مهلت‌ها
frontend/src/
  app/         # صفحات App Router
  components/  # اجزای مشترک رابط
  lib/         # کلاینت API و typeهای تولیدشده
contracts/     # openapi.json تحویلی
```

تصمیم مالی، امتیازدهی و مجوز فقط در بک‌اند اجرا می‌شوند و در TypeScript تکرار نشده‌اند.
بررسی سریع فرم در مرورگر فقط برای تجربهٔ کاربر است؛ سرور همهٔ ورودی‌ها را دوباره
اعتبارسنجی می‌کند.

## محدودیت‌های شناخته‌شده

- پرداخت و بازپرداخت **شبیه‌سازی‌شده‌اند**؛ درگاه بانکی، شمارهٔ کارت و امانت‌داری وجه ساخته
  نشده است. وصول وجه تعمیر هم جزو این نسخه نیست.
- اتصال به ترب فقط لینک جست‌وجو و ثبت دستی است. خزش، API فرضی، موجودی زنده و خرید خودکار
  وجود ندارد.
- «مرجع بازار» در این نصب از دادهٔ نمونه پر شده و مرجع واقعی نیست؛ حالت پیش‌فرض
  `bootstrap` است.
- OCR تصویر، ارسال تصویر به مدل، صوت، RAG و زیرساخت برداری، اشتراک خصوصی متخصص، پیامک و
  اپ بومی پیاده‌سازی نشده‌اند.
- کیفیت حالت live آزموده نشده است؛ قبولی حالت mock معادل آزمون مدل واقعی نیست. برای سنجش،
  `backend/evaluation/cases.json` با ۲۴ پروندهٔ فارسی برچسب‌خورده آماده است.
- تعویض متخصص حداکثر یک بار و فقط پیش از شروع کار ممکن است.
